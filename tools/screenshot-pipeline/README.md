# 无头浏览器截图管线

四步：登录拿会话 → 抓页面 HTML → 把 `/assets/...` 相对路径重写成实例的绝对 URL →
无头 Chromium 打开本地文件截图。给"必须看图、不能读 HTML 猜"的验证场景用。

**这里不放脚本。** 二十行 curl + chromium，照上面四步谁都写得出来；写死了实例地址
和口令的那份对别人没有价值。**有价值的是下面两节**——那三条限制和那个教训，
不知道的话截出来的图会把你带沟里。

**截完必须用图像查看工具真的看一遍**，不能只读中间产物的 HTML 去猜页面
长什么样——HTML 结构对、渲染结果未必对（层叠顺序、溢出、图标是否真的画出
来，这些只有图能告诉你）。

## 已知限制

管线本身有三处会制造"看起来像 bug、实际是管线限制"的假象，看截图之前先知道
这三条，省得误判：

| 限制 | 表现 | 原因 |
|---|---|---|
| 跨源资源受限 | `mask-image` 引用的图标空白；页面里的外部图片（如头像）显示为破图 | 页面走 `file://` 协议打开，跨源请求受限，不是资源本身有问题 |
| 拿不到客户端渲染的实时 DOM | Vue 渲染的页面（例如 Actions 日志）看到的是初始骨架，不是运行时内容 | 管线抓的是服务端返回的 HTML，不会跑起客户端的 JS 应用状态 |
| 依赖 origin 的 JS 功能失真 | 例如克隆协议切换按钮显示 `NULL`——真实页面上正常 | 这类功能在 JS 里判断当前 `location.origin`，`file://` 页面的 origin 跟实例不一样，逻辑分支走错 |

这三条**不是要修的 bug**，是管线的固有代价——真要验证这些部分，得直接在
浏览器里打开实例 URL 看，不能靠这条管线。

## 一个真实教训：空 cookie jar 让截图静默拍到未登录页

早期版本用 `set -o pipefail` 配 `grep` 从登录页里提取 CSRF token。`grep`
没匹配上时管道整体失败、脚本中止，**留下一个空的 cookie jar 文件**。
下一次运行时，脚本只看"jar 文件存不存在"来判断要不要重新登录——文件在
（哪怕是空的），就跳过登录直接抓页面，**静默拿到了未登录状态的页面**，
截图看起来"正常"，实际内容完全不对。

现在的版本换了判据：**用 `/user/settings` 能不能访问（HTTP 200）来判定会话
有效**，不看 jar 文件存不存在——jar 是空文件也好、过期也好，这一步都能测
出来，测不过就重新走登录流程：

```bash
code=$(curl -sS -b "$J" -o /dev/null -w '%{http_code}' "$B/user/settings" 2>/dev/null || echo 000)
if [ "$code" != "200" ]; then
  rm -f "$J"
  # ...重新登录...
fi
```

另外，这个登录表单**没有隐藏的 CSRF 字段**，直接 POST `user_name` +
`password` 就能登录——最早那版去抓 CSRF token 本身就是多余的一步，才会在
这一步引入上面这个 bug。
