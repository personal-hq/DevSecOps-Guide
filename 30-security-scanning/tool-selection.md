# 商业与进阶工具选型

新工具准入标准与 [05-architecture.md](../05-architecture.md) 一致：闭的是哪个环？谁看输出？不上它现在漏了什么？答不上第二问的一律不上。下面每个工具都先过一遍这三问，再展开。

## 用准入标准筛一遍

| 工具 | 解决什么 | 现在的缺口 | 判断 |
|---|---|---|---|
| Cosign/Sigstore | 制品完整性 | 现在什么都不漏——没有强制验证的部署路径 | 等触发 |
| DefectDojo | 发现→修复（确实缺） | 2 个仓库时缺口不明显 | 规模到了再上 |
| Dependency-Track | 组合爆炸半径 | 服务少时定时 trivy 够 | 20+ 服务再上 |
| SonarQube CE | 代码质量 | linter 能覆盖大半 | 多数情况不值 |
| Burp Pro | 手工测试 | 确实漏了，但缺的是人不是工具 | 跟着人走 |

## Cosign + Sigstore

解决的是"证明这个制品确实是我的流水线构建的"。**签名的价值全在验证那一步**——如果部署路径上没有任何环节强制校验签名，cosign 只是给 CI 流程加几十秒的仪式，谁都可以照样部署一个未签名的镜像。

**触发条件**：有一条能强制拒绝未签名制品的部署路径——k8s 准入控制，或者部署脚本里的硬门。没有这条，先不上。

另一个需要提前想清楚的决策点：Sigstore 的 keyless 模式依赖公共透明日志（Rekor）和公共 CA（Fulcio），**构建身份会进公开日志**。内部公司能否接受这一点要先确认；不接受就只能用密钥模式，但密钥模式又绕回了密钥管理问题。

## DefectDojo

补的正是"谁看报告、谁负责、修没修"这个洞——这是四条闭环里最容易缺失的一环。但它的价值和发现量成正比，**2 个仓库时是大炮打蚊子**，还多一个 Django + 数据库要运维、要备份。

**触发条件**：≥3 个扫描器 × ≥10 个仓库。在那之前，Forgejo issue 加 label 就够，零运维。

## Dependency-Track

trivy 是**扫描视角**——构建这一刻这份代码有什么 CVE。Dependency-Track 是**清单视角**——三个月前发布的版本，今天新爆出来的 CVE 影响不影响它。

不可替代的是**组合爆炸半径查询**：类似 log4j 事件里"这 50 个服务里哪些用了、用的什么版本"这种问题，定时重扫每个仓库回答不了，得先有一份跨服务的清单。

**触发条件**：20+ 服务。**但现在就该做的**：让 trivy 输出 CycloneDX 格式的 SBOM 存成 CI artifact——免费，且是将来上 Dependency-Track 的前置条件。SBOM 是攒出来的，不是需要时现补的。

## SonarQube CE vs Developer+

| | CE（免费，LGPL v3） | Developer+ |
|---|---|---|
| 质量：重复率/复杂度/坏味道 | ✅ | ✅ |
| 覆盖率导入 + 质量门禁 | ✅ | ✅ |
| **PR/非主干分支分析** | ❓ **未验证，采购前必须实测** | ✅ |
| 跨文件污点分析 | ❌ | ✅ |
| 组合视图/OWASP 报告 | ❌ | Enterprise |

那个 ❓ 是采购决策的关键：**如果 CE 真的不能分析 PR，"Sonar 当 PR 门禁"这个用法在 CE 上根本不成立**，这条必须在花钱之前用真实仓库测出来，不能假设。

判断：CE 的安全规则弱，而且和 semgrep 的覆盖重叠，它的价值在**质量维度**（重复率、复杂度、坏味道），不在安全。但同样是质量维度，用 golangci-lint/eslint/ruff + CI 覆盖率阈值成本低一个数量级，且不需要多运维一个服务。**为了"多一个安全扫描"上 Sonar CE 是净亏损。**

Developer 版的触发条件：代码量大到 semgrep OSS 的漏报有实际代价 / 确实需要 PR 门禁（前提是上面那个 ❓ 已经验证）/ 多语言混合项目。

## Semgrep OSS vs 商业版

| | OSS（LGPL-2.1） | Code（Pro） | Supply Chain | Secrets |
|---|---|---|---|---|
| 单文件模式匹配 | ✅ | ✅ | | |
| 跨文件污点分析 | ❌ | ✅ 核心差异 | | |
| 可达性分析 | ❌ | | ✅ 核心差异 | |
| 密钥有效性验证 | ❌ | | | ✅ |
| 分诊/PR 评论/策略 | 自己搭 | AppSec Platform（SaaS） | | |

实测的两个架构含义：

1. `install-semgrep-pro` 装的是**单独的引擎二进制**，要 login 到 semgrep.dev，不是填一个许可证密钥那么简单
2. **`--config auto` 会把项目 URL 发到 semgrep.dev 登录**——内部服务器要注意这条数据外流路径。我们用的是固定规则集 `p/default`，不是 `auto`，不受这条影响

**判断：要为 semgrep 花钱，Supply Chain 优先级高于 Code（Pro）。** 可达性分析回答的是"你的代码到底调没调到那个受影响函数"，直接砍掉依赖分诊里最大的一块成本——典型项目里大部分依赖 CVE 是不可达的，可达性分析能把这些直接排除掉。跨文件污点分析解决的是"可能漏报"这个还没造成实际损失的问题，优先级更低。

⚠️ 价格与功能边界会变，以上未验证，采购前自己确认。

## 商业工具按"钱买的是什么"分类

| 花的钱买什么 | 什么时候值 | 优先级 |
|---|---|---|
| 人的时间（渗透测试/招人） | 有真实用户和数据那天 | 🥇 第一笔钱 |
| 更深静态分析 | OSS 漏报/误报有实际代价 | 🥈 |
| 依赖分诊质量（Snyk/Mend/Sonatype） | 噪音让人开始忽略告警 | 🥉 |
| 交互式手工测试（Burp Pro） | 有人专职用它 | 跟着人走 |
| 托管免运维（GHAS/GitLab Ultimate） | 不想自运维 | 看团队 |
| 合规交付物（GRC） | 有认证/审计要求 | 被动触发 |

三个判断：

1. **第一笔钱不要花在扫描器上。** 扫描器的边际收益递减极快，OSS 已经覆盖了绝大部分**可自动化发现**的问题；真正造成损失的那些——越权、支付流程绕过、状态机缺陷、业务逻辑滥用——只有人能找到。一次外部渗透测试的价格通常低于一年的商业 SAST 订阅，发现的高危往往更多。
2. **Burp Pro 是给人用的，不是给流水线用的**，和 ZAP 不是竞品。没有那个专职用它的人，买了就是买了一个没人开的软件。需要接入 CI 的是 Burp Enterprise，是另一个价位、另一个决策。
3. **商业工具消除不了分诊成本**，换来的是界面和支持，不是工作量本身。两个隐性成本容易被忽略：按开发者数计费（团队从 30 人到 150 人时费用不是线性涨的），以及供应商锁定（规则、SBOM、报告格式都是私有的，迁移成本随时间推移只会更高）。
