# 自建 Git 服务

自建 Git 服务（以 Forgejo 为例）的形态选择、存储方式、两处部署期踩过的实测缺陷、
SSH 接入方式的取舍、备份与恢复演练、首页配置，以及升级流程。

## 一、形态选择：Compose vs 二进制 vs k3s

容器化（Docker Compose）和裸机二进制安装最本质的差异是**版本固化**：镜像把
git、SSH 服务、运行时库的版本一起打包定型，升级是显式改一行 `image:` 标签；
二进制安装则把这些版本绑在宿主自己的包管理器上，宿主一次跟 Git 服务本身无关的
系统升级，就可能顺带把 git 或 SSH 服务换成一个没验证过的版本。少一类环境漂移，
不是"部署起来更快"这种量级的差异。

k3s 是第三个候选，而且不是假设性的选项——这台宿主本身就在跑 k3s，承载着别的
服务（eh、pingcdn）。没有把 Git 服务也放进去，理由是：**代码仓库是长期有状态
数据，不该绑在一个默认预期会被反复重建、重新调度的集群上**。k8s workload 的
设计前提是实例可以随时被杀掉重建、漂移到别的节点，状态靠 PV/PVC 这层额外抽象
兜底；而一个 Git 服务的全部价值几乎就是仓库数据本身，集群编排能换来的（自愈、
水平扩展）在单实例自用场景下用不上，换来的只是"数据到底在哪个节点的哪个 PV
上"这类额外的心智负担。

| 形态 | 版本固化 | 状态位置 | 适用场景 |
|---|---|---|---|
| Docker Compose | 镜像锁定，升级 = 改 tag | bind mount 到宿主路径，一眼可见 | 单实例自用，本节场景 |
| 二进制 + systemd | 依赖宿主包管理器，随系统升级漂移 | 路径由安装者自己约定 | 需要精确控制系统集成的场景 |
| k3s | 镜像锁定，同 Compose | 需要 PV/PVC 抽象，重建/调度是常态 | 真正需要跨节点调度或自愈的负载 |

## 二、存储：bind mount 而非 named volume

这台宿主的 `/var/lib/docker/volumes` 下已经有 **274 个属于其它项目的 named
volume**（pingcdn、EnHeim 等），外加约 14GB 的 build cache。这不是一个干净、
只属于这一个服务的环境——任何在这台机器上工作的人一次 `docker volume prune`，
就会把这个服务用到的 named volume，连同那 274 个里"当下看起来没在用、其实不能丢"
的大部分一起清掉，而且这条命令本身不会问"这些数据重要吗"。

Bind mount 到宿主某个具体路径下不受这条命令影响——它根本不是 docker 管理的
对象，`docker volume prune` 看不见也碰不到它。附带的好处是备份路径肉眼可见：
数据实际落在磁盘的什么位置一目了然，不需要先 `docker volume inspect` 才能找到
它躺在哪个 `/var/lib/docker/volumes/<hash>/_data` 里。

由此产生一条写 compose 文件时必须遵守的约束：**每一个 volume 挂载都必须是
bind mount**（`/host/path:/container/path`），不能是裸的 `name:` volume。这条
约束还有一个容易漏掉的推论——挂载必须覆盖镜像自身在 Dockerfile 里声明的每一个
`VOLUME` 路径，否则 Docker 会用匿名卷悄悄补上那个缺口，且不报错。下一节的第二个
实测缺陷，就是这条推论被忽略之后出的问题。

## 三、两个部署期实测缺陷

### `START_SSH_SERVER=true` 导致容器崩溃循环

**症状**（实测）：把 `START_SSH_SERVER` 设为 `true`、`SSH_LISTEN_PORT` 留在
默认值（容器内 22 端口）后，容器进入崩溃循环，日志原文：

```
Failed to start SSH server: listen tcp :22: bind: address already in use
```

**根因**：这个镜像不是 rootless 变体，它用 s6 无条件启动一个系统级 `sshd`——
不管 `START_SSH_SERVER` 是什么值，这个系统 sshd 都会常驻并占住容器内 22 端口。
`START_SSH_SERVER=true` 打开的是内建的 Go SSH 服务器，是另一个独立进程；如果把
它也配置成监听容器内 22 端口，两个进程抢同一个端口，后启动的那个直接崩溃退出，
s6 拉起重试，循环往复。

**修法**：把 `SSH_LISTEN_PORT` 改到非 22 的端口（本例中用 2222），让内建 Go SSH
服务器监听 2222，系统 sshd 继续占着容器内 22（不对外发布，只在 compose 内部
网络可达）。两者不再抢端口。修复后端到端验证：容器 `RestartCount` 保持 0、
稳定监听 2222，一次真实 `git clone ssh://...` 成功（exit 0，提交内容存在）。

系统 sshd 本可以用 s6 的 `down` 文件掩掉，但这需要碰镜像自带的 init 逻辑，
"少一个空转进程"的收益和"改镜像 init 可能弄坏启动流程"的风险不成比例，本例中
选择不做，只确认它已不再对外发布。

### postgres 匿名卷泄漏

**症状**（实测）：bind mount 只挂了 PGDATA 叶子目录（例如容器内
`/var/lib/postgresql/18/docker`），compose 配置本身不报任何错，`docker compose
up -d` 干净退出。但卷计数变了：部署前 `docker volume ls -q | wc -l` 是 274，
部署后变成 275——多出一个没人声明过的匿名卷。

**根因**：`postgres:18.x` 镜像的 Dockerfile 声明了 `VOLUME /var/lib/postgresql`
——是 PGDATA 的**父目录**，不是 PGDATA 叶子本身。只挂叶子目录时，Dockerfile
声明的这个父目录路径仍然"没人管"，Docker 的行为是**静默**创建一个匿名卷去填补
它——不报错、不提示，配置看起来完全正常，唯一的痕迹就是卷计数多了一个。

**修法**：bind mount 直接挂父目录（`/var/lib/postgresql`），覆盖整个
Dockerfile 声明的 `VOLUME` 路径；postgres 启动时会自己在这个目录下
`mkdir -p` 出实际的 PGDATA 子目录。挂载覆盖了声明路径，就不再有缺口，
匿名卷不会被创建。

**可复用的验收方法**：只要用的是别人写的镜像，写 bind mount 之前应该先确认
这个镜像的 Dockerfile 有没有 `VOLUME` 声明，挂载必须覆盖到那个声明路径，而
不是想当然地只挂应用实际读写的叶子目录。不确定有没有漏挂时，最直接的验收就是
这次用的方法：改动前后各跑一次 `docker volume ls -q | wc -l`，数字变了就说明
有声明路径没被覆盖到，再配合 `docker volume ls -qf dangling=true` 定位新增的
是哪个卷、对应哪个容器的哪段路径漏挂了。这个方法不针对 postgres，对任何
第三方镜像都适用。

## 四、SSH 接入：内建 Go 服务器 vs 系统 sshd

排查 SSH 相关问题时最容易翻车的地方，是把三个端口概念混为一谈——它们互相独立，
改一个不会影响另外两个：

| 变量 | 例值（本例） | 实际含义 |
|---|---|---|
| 宿主发布端口 | 21022 | 从宿主（或隧道）连进来时用的端口 |
| `SSH_LISTEN_PORT` | 2222 | 内建 Go SSH 服务器在**容器内部**真正监听的端口 |
| `SSH_PORT` | 21022 | **仅仅是显示用**——写进 clone URL 里的端口号，本身不是任何进程的监听端口 |

`SSH_PORT` 和 `SSH_LISTEN_PORT` 名字像，作用完全不同：改 `SSH_PORT` 不会让任何
监听行为发生变化，只会让生成的 clone 地址里端口号跟着变。排查"连不上"类问题时，
该查的是 `SSH_LISTEN_PORT` 和宿主发布端口是否对应，跟 `SSH_PORT` 无关——查错
变量是这里最常见的浪费时间的方式。

选内建 Go SSH 服务器、而不是走系统 `sshd`，理由是**免维护**：内建服务器直接拿
数据库里的公钥做认证，不需要一份 `authorized_keys` 文件——这个文件本身就是会
漂移的状态（账号、公钥的增删都要求它被正确重写），官方专门提供一条
`admin regenerate keys` 命令去修复它跑偏的情况，这件事本身就说明它是个已知的
脆弱点。代价是 Go 实现的 SSH 协议栈支持的加密套件和客户端选项比 OpenSSH 少——
客户端用了某些冷门密钥类型或加密算法时可能连不上，这种情况下才需要考虑退回
系统 sshd。

## 五、备份与恢复演练

`forgejo dump` 是单命令全量备份，把仓库、数据库、配置和自定义资源（比如
[50-ui-theming](../50-ui-theming/) 里改的品牌化静态文件）打进一个归档——已
验证：归档里 `data/public/assets/...` 路径下的自定义静态资源确实齐全，不是只
备份了数据库。备份脚本本身要写扎实：`set -euo pipefail`，任何一步失败都是非
零退出码，不会静默吞掉失败。这些是卫生条件，不是本节重点。

**本节真正的重点：一句诚实的话，比一条绿色的 cron 记录更重要。** 备份脚本
"目前跑通"、"退出码 0"、"保留了最近 N 份"，这些都只证明 **dump 命令本身没
崩溃**，不证明**从这份 dump 真的能恢复出一个可用实例**。这正是
[00-principles.md 第 2 条](../00-principles.md#2-错误消失不等于修好了)的例子
——拿"没报错"当"结果正确"的判据。恢复流程哪怕写得再详细（解包归档、
drop+recreate 数据库 schema 后灌 SQL、把仓库归档解到 repositories 目录、
修 ownership、拉起服务……），只要没有**端到端跑过一次**，就不知道那份 SQL
dump 格式对不对、ownership 步骤有没有遗漏、恢复后服务是否真的启动得起来。
"已文档化"和"能恢复"是两回事：有恢复流程但从没演练过，只能算"未知是否可用"，
不能当成"已具备灾难恢复能力"来汇报。

**验收方法**（实测，可复用）：不确定备份归档里有没有漏东西时，别想当然地用
`unzip -l` 查——如果宿主机没装 unzip，这条命令会返回空结果，而空结果和"确实
没有内容"长得一模一样，很容易得出"备份丢了东西"的错误结论。应该改用语言自带、
不依赖宿主装了什么工具的方式去读，比如 Python 的 `zipfile` 模块列出归档内容、
逐条核对预期路径是否在场。这是
[00-principles.md 第 4 条](../00-principles.md#4-工具缺失会伪装成事实)的例子：
工具本身缺失，会伪装成"查询结果就是空的"这个事实。

同样重要、但独立的另一条：备份产物存在哪里也有讲究——如果备份和线上数据在
同一块盘上，一次磁盘故障或一次误操作的 `rm -rf`，会把实例和它的全部备份一起
抹掉。真正抗灾要求复本落在别的磁盘或别的主机上，这一步和"备份脚本本身写得
可靠"是两件独立的事，不要因为脚本工整就默认这一步也做了。

## 六、首页与匿名访问

`LANDING_PAGE=login` 把匿名访客的落地页从 Forgejo 默认首页换成登录页——设置后
未登录访问直接进登录表单（改造结果见 50-ui-theming/README.md 的记录）。

默认首页面向的是外部访客、面向"要不要选这个产品"这层决策，这对一个只有内部
团队使用、不需要对外做任何展示的服务器没有意义。同一个仓库里已经验证过的外链
清理（隐藏顶栏指向上游官方站的 Help 链接、去掉页脚版本号和"由 XX 提供支持"字样）
是同一个思路在另一个位置的应用——都是把面向公众的产品痕迹从一个内部工具上去掉，
详细机制见 [50-ui-theming](../50-ui-theming/)，这里不重复。

## 七、升级

升级前有两条纪律，比流程本身更容易被跳过：

1. **先跑一次备份**（`backup.sh` 或等价的 `forgejo dump`）。参见上一节——升级
   出问题时，"能回到升级前状态"这件事本身依赖这一步先做了。
2. **镜像 tag 钉死到具体 patch 版本，不用浮动 tag**（不用类似 `:16` 或
   `:latest` 这样的写法）。对内部团队提供服务的软件，patch 版本里相当一部分是
   安全修复，把升级钉成"改一行 tag、手动跑一次流程"这样的显式动作，比让容器
   在某次重启后静默换成一个没人验证过的版本要可控。

流程：

1. 改 `docker-compose.yml` 里的 `image:` 标签，换成新的 pinned 版本
2. `docker compose pull`
3. `docker compose up -d`
4. 跟日志确认干净启动，同时看 `RestartCount` 是否保持 0
   （`docker inspect <容器> --format '{{.RestartCount}}'`）——只看进程是否存活
   不够，崩溃循环重启后进程"看起来在跑"，但 `RestartCount` 会把它其实一直在
   重启这件事暴露出来
5. 冒烟测试：调用一个带版本信息的接口，确认返回的版本号真的变了，而不是命中
   了缓存的旧响应

Postgres 是例外：主版本升级（比如 18.x → 19.x）不是简单的 tag bump，数据文件
格式可能不兼容，需要 `pg_upgrade` 或者显式的"导出旧版本数据 → 起新版本 → 导入"
迁移流程。当成普通 tag bump 直接改了重启，大概率是数据目录起不来。
